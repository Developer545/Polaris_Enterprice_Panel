1. RESUMEN EJECUTIVO
================================================================================

La facturación electrónica en El Salvador funciona mediante Documentos Tributarios Electrónicos, conocidos como DTE. Un sistema POS moderno no debe limitarse a generar una factura visual o un PDF; debe generar un JSON tributario válido, firmarlo electrónicamente, transmitirlo al Ministerio de Hacienda, recibir una respuesta oficial, almacenar el sello de recepción y conservar evidencia fiscal completa.

Para que el JSON sea aceptado por Hacienda, debe cumplir tres grandes condiciones:

1. Requisito administrativo:
   - El contribuyente debe estar autorizado como emisor DTE.
   - Debe contar con usuario, contraseña o credenciales de acceso al ambiente de Hacienda.
   - Debe tener firma/certificado electrónico habilitado para firmar los documentos.
   - Debe tener configurados los datos fiscales correctos del emisor, establecimiento, punto de venta y actividad económica.

2. Requisito técnico:
   - El DTE debe construirse según el JSON Schema oficial correspondiente al tipo de documento.
   - Debe firmarse mediante el mecanismo aceptado por Hacienda, normalmente en formato JWS.
   - Debe enviarse a la API oficial de recepción con token válido.
   - Deben respetarse catálogos oficiales: ambiente, tipo de DTE, tipo de operación, tipo de transmisión, departamento, municipio, tipo de documento, unidad de medida, forma de pago, tributos, entre otros.

3. Requisito contable/fiscal:
   - Los totales deben cuadrar exactamente.
   - El cuerpo del documento debe coincidir con el resumen.
   - El IVA, descuentos, retenciones, ventas gravadas, exentas y no sujetas deben calcularse correctamente.
   - El documento debe conservarse con su JSON original, JSON firmado, respuesta de Hacienda, sello de recepción y representación gráfica.

Para tu stack propuesto, la arquitectura recomendada es:

- Backend: NestJS
- Frontend: Next.js
- ORM: Prisma
- Base de datos: PostgreSQL
- Cache y colas: Redis + BullMQ
- Logs: Pino
- Tablas avanzadas: TanStack Table
- Estado de datos frontend: TanStack Query
- UI empresarial: Ant Design
- Validación JSON Schema: AJV
- Validación de DTO: class-validator o Zod
- Generación PDF: Playwright
- Firma DTE: servicio interno separado o microservicio firmador

4. CONCEPTOS CLAVE
================================================================================

DTE:
Documento Tributario Electrónico. Es el documento fiscal digital generado en formato JSON, firmado electrónicamente y enviado a Hacienda.

JSON DTE:
Archivo estructurado que contiene identificación, emisor, receptor, detalle de productos o servicios, resumen, pagos, tributos, apéndice y otros bloques según el tipo de documento.

JSON Schema:
Estructura técnica que define campos permitidos, tipos de datos, longitudes, patrones, campos requeridos y restricciones de cada tipo de DTE.

JWS:
JSON Web Signature. Mecanismo utilizado para firmar documentos JSON y garantizar que no fueron alterados después de su firma.

Código de generación:
UUID versión 4 generado por el emisor. Sirve como identificador único del DTE dentro del ecosistema de facturación electrónica.

Sello de recepción:
Código emitido por Hacienda cuando el DTE cumple los requisitos y es recibido/procesado exitosamente. Es una evidencia crítica para la validez del documento.

Representación gráfica:
PDF, ticket o vista imprimible del DTE. No sustituye el JSON firmado ni la respuesta de Hacienda.

5. REQUISITOS PARA CONECTARSE A HACIENDA
================================================================================

Para conectar tu POS a la API de Hacienda necesitas:

1. Autorización como emisor DTE
   El contribuyente debe estar habilitado para emitir documentos tributarios electrónicos. Esto se gestiona ante el Ministerio de Hacienda.

2. Credenciales de acceso
   Hacienda asigna credenciales para consumir el servicio de autenticación y obtener token.

3. Certificado o firma electrónica
   El emisor debe firmar electrónicamente los DTE. La firma debe corresponder al contribuyente/emisor autorizado.

4. Configuración fiscal del emisor
   El sistema debe guardar:
   - NIT
   - NRC
   - Nombre legal
   - Nombre comercial
   - Código de actividad económica
   - Descripción de actividad económica
   - Tipo de establecimiento
   - Código de establecimiento MH
   - Código interno de establecimiento
   - Código de punto de venta MH
   - Código interno de punto de venta
   - Dirección fiscal
   - Departamento
   - Municipio
   - Teléfono
   - Correo de facturación

5. Catálogos oficiales
   Deben cargarse y mantenerse actualizados:
   - Ambiente
   - Tipo de documento DTE
   - Tipo de generación
   - Tipo de modelo
   - Tipo de operación
   - Tipo de contingencia
   - Tipo de establecimiento
   - Tipo de item
   - Unidad de medida
   - Tipo de documento del receptor
   - Departamento
   - Municipio
   - Actividad económica
   - Tributos
   - Forma de pago
   - Condición de operación
   - Plazo
   - Moneda

6. JSON Schema oficial
   Cada DTE tiene su propio schema. No debes inventar la estructura. Tu backend debe validar el JSON contra el schema correcto antes de firmarlo.

6. APIs PRINCIPALES DE HACIENDA

6.1 Servicio de autenticación

Ambiente de pruebas:
https://apifacturatest.mh.gob.sv/auth

Ambiente de producción:
https://apifactura.mh.gob.sv/auth

Método:
POST

Content-Type:
application/x-www-form-urlencoded

Parámetros:
user=usuario_asignado
pwd=password_asignado

Respuesta esperada:
{
  "status": "OK",
  "body": {
    "user": "usuario",
    "token": "Bearer ...",
    "tokenType": "Bearer"
  }
}

Notas técnicas:
- El token se usa para consumir los servicios de recepción.
- Según la guía oficial, en pruebas la vigencia se ha manejado como 48 horas y en producción como 24 horas.
- Tu backend debe guardar el token en Redis con expiración menor a la vigencia oficial.
- Nunca guardes el token en frontend.

6.2 Servicio de recepción DTE

Ambiente de pruebas:
https://apifacturatest.mh.gob.sv/fesv/recepciondte

Ambiente de producción:
https://apifactura.mh.gob.sv/fesv/recepciondte

Método:
POST

Headers:
Authorization: Bearer TOKEN
Content-Type: application/json

Body general:
{

  "idEnvio": 1,
  "version": 1,
  "tipoDte": "01",
  "documento": "JWS_DEL_DTE_FIRMADO",

}

Respuesta esperada:
{
  "version": 1,
  "ambiente": "00",
  "versionApp": 1,
  "estado": "PROCESADO",
  "codigoGeneracion": "UUID",

  "fhProcesamiento": "dd/MM/yyyy HH:mm:ss",

Estados internos recomendados:
- BORRADOR
- GENERADO
- VALIDADO_SCHEMA
- FIRMADO
- ENVIANDO
- PROCESADO
- PROCESADO_CON_OBSERVACIONES

- ERROR_CONEXION
- CONTINGENCIA
- ANULADO

8. BLOQUE IDENTIFICACION
================================================================================

Ejemplo conceptual:

{
  "version": 1,
  "ambiente": "00",
  "tipoDte": "01",
  "numeroControl": "DTE-01-M001P001-000000000000001",
  "codigoGeneracion": "550E8400-E29B-41D4-A716-446655440000",
  "tipoModelo": 1,
  "tipoOperacion": 1,
  "tipoContingencia": null,
  "motivoContin": null,
  "fecEmi": "2026-05-16",
  "horEmi": "10:30:00",
  "tipoMoneda": "USD"
}

Validaciones:
- ambiente debe ser "00" para pruebas o "01" para producción, según catálogo oficial.
- codigoGeneracion debe ser UUID v4.
- numeroControl debe respetar formato autorizado.
- fecEmi debe respetar formato de fecha.
- horEmi debe respetar formato de hora.
- tipoDte debe coincidir con el schema usado.
- tipoContingencia y motivoContin deben usarse solo si aplica.
- tipoMoneda usualmente será USD.

Errores comunes:
- Enviar UUID en minúsculas cuando el schema exige mayúsculas.
- Usar un numeroControl duplicado.
- Enviar fecha/hora con formato incorrecto.
- Enviar ambiente de pruebas con credenciales de producción o viceversa.

11. BLOQUE CUERPO DOCUMENTO
================================================================================

Este bloque representa las líneas del carrito del POS.

Ejemplo conceptual:
{
  "numItem": 1,
  "tipoItem": 1,
  "numeroDocumento": null,
  "cantidad": 2,
  "codigo": "P001",
  "codTributo": null,
  "uniMedida": 59,
  "descripcion": "Corte de cabello",
  "precioUni": 5.00,
  "montoDescu": 0.00,
  "ventaNoSuj": 0.00,
  "ventaExenta": 0.00,
  "ventaGravada": 10.00,
  "tributos": null,
  "psv": 0.00,
  "noGravado": 0.00,
  "ivaItem": 1.15
}

Reglas:
- numItem debe iniciar en 1 y ser correlativo.
- cantidad debe ser mayor que cero.
- precioUni no debe ser negativo.
- descripcion es obligatoria.
- uniMedida debe venir del catálogo oficial.
- tipoItem debe venir del catálogo oficial.
- no deben enviarse líneas vacías.
- no deben enviarse productos con cantidad cero.
- ventaGravada, ventaExenta y ventaNoSuj deben calcularse correctamente.
- ivaItem debe calcularse según el tipo de documento y las reglas tributarias aplicables.

14. FLUJO TÉCNICO RECOMENDADO PARA EL POS
================================================================================

Flujo ideal:

1. Cajero crea venta en POS.
2. Frontend envía carrito al backend.
3. Backend valida productos, cliente, usuario, caja, sucursal y punto de venta.
4. Backend calcula totales con Decimal.js o Prisma Decimal.
5. Backend guarda venta local en estado BORRADOR.
6. Backend genera JSON DTE.
7. Backend valida JSON contra JSON Schema con AJV.
8. Backend genera codigoGeneracion UUID v4.
9. Backend genera numeroControl.
10. Backend firma el JSON.
11. Backend solicita token a Hacienda o usa token vigente desde Redis.
12. Backend envía DTE firmado a recepción.
13. Hacienda responde.
14. Backend guarda:
    - JSON original
    - JSON firmado
    - respuesta completa
    - sello de recepción
    - observaciones
    - estado
15. Backend genera PDF o ticket.
16. Frontend muestra resultado.
17. Si falla, se envía a cola de reintento o contingencia.

17. REDIS, COLAS Y REINTENTOS
================================================================================

Redis debe usarse para:

1. Cachear token de Hacienda.
2. Manejar colas de emisión DTE.
3. Manejar reintentos.
4. Controlar bloqueo de correlativos.
5. Evitar doble emisión.
6. Procesar contingencia.

Recomendación con BullMQ:

Colas:
- dte.generate
- dte.sign
- dte.send
- dte.retry
- dte.contingency
- dte.pdf

Regla:
El frontend no debe esperar indefinidamente a Hacienda. Debe poder mostrar un estado como "procesando", mientras el backend termina la transmisión.

18. PINO Y LOGS PROFESIONALES
================================================================================

Usa Pino para registrar eventos técnicos, pero nunca registres información sensible completa.

Redactar:
- Authorization
- token
- pwd
- password
- clave privada
- certificado
- jsonFirmado
- firma
- datos completos de cliente si no son necesarios

Ejemplo de redacción conceptual:

redact: [
  'req.headers.authorization',
  'token',
  'pwd',
  'password',
  'certificado',
  'clavePrivada',
  'jsonFirmado'
]

Eventos a registrar:
- DTE_GENERATED
- DTE_SCHEMA_VALIDATED
- DTE_SIGNED
- HACIENDA_AUTH_OK
- HACIENDA_AUTH_ERROR
- DTE_SENT
- DTE_PROCESSED
- DTE_REJECTED
- DTE_RETRY
- DTE_CONTINGENCY_STARTED
- DTE_ANNULLED

21. ERRORES COMUNES
================================================================================

1. JSON inválido:
   - Campo faltante.
   - Campo extra.
   - Tipo incorrecto.
   - null incorrecto.
   - string vacío donde no aplica.
   - catálogo incorrecto.

2. Firma inválida:
   - Se modificó el JSON después de firmarlo.
   - Certificado incorrecto.
   - NIT del emisor no coincide.
   - Formato JWS inválido.

3. Totales incorrectos:
   - Descuento mal calculado.
   - IVA mal calculado.
   - Redondeo diferente.
   - pagos no coinciden con totalPagar.

4. Error de autenticación:
   - Token expirado.
   - Credenciales incorrectas.
   - Ambiente incorrecto.
   - Usuario sin permisos.

5. Error de comunicación:
   - 500
   - 502
   - 503
   - 504
   - timeout
   - caída de internet

25. CONCLUSIÓN
================================================================================

Para construir un POS empresarial compatible con facturación electrónica en El Salvador, el núcleo del sistema debe estar en el backend. El frontend solo debe capturar la venta y mostrar el resultado. La generación del JSON, cálculo de totales, validación, firma, transmisión y almacenamiento fiscal deben hacerse en NestJS.

Regla principal:

Frontend vende.
Backend calcula.
Backend genera.
Backend valida.
Backend firma.
Backend transmite.
Backend guarda evidencia fiscal.

El JSON será aceptado por Hacienda si cumple:

1. Schema correcto.
2. Catálogos correctos.
3. Totales exactos.
4. Emisor autorizado.
5. Firma válida.
6. Credenciales válidas.
7. Ambiente correcto.
8. Código de generación único.
9. Número de control válido.
10. Documento no alterado después de firmar.
